# SLA/SLO — Platform Service Levels by Layer

**Scope:** the concrete freshness, data-quality, and latency targets referenced by [IMPROVEMENTS_AND_RESEARCH.md §2 item 8](../../IMPROVEMENTS_AND_RESEARCH.md#2-lacunas-do-design-original-preenchidas-nesta-consolidação) and required by [ROADMAP.md Sprint 16](../../ROADMAP.md). This is the reference table the **Monitoring Agent** and **Data Quality Agent** ([ARCHITECTURE.md §15](../../ARCHITECTURE.md#15-layer-12--mcp--agentic-ai)) alert against, and the table [`dq_score_drop.md`](dq_score_drop.md) and [`pipeline_failure.md`](pipeline_failure.md) assume when they say a metric "dropped below baseline."

Per [ARCHITECTURE.md §21](../../ARCHITECTURE.md#21-production-readiness--honesty-note), these are portfolio-scale targets — sized for a personal-budget sandbox provisioned on demand, not a 24/7 production SLA with a paging rotation. They exist to demonstrate that SLOs are defined, measured, and acted on, the same rigor a production system would use.

## 1. Data quality SLOs

| Metric | Target | Basis |
|---|---|---|
| Platform Data Quality Score (rollup) | **>= 99.5%**, alert on any drop below this baseline | Current measured baseline is 99.83% ([`data_quality/reports/dq_report.json`](../../data_quality/reports/dq_report.json), generated by the GX Core checkpoint run) — 99.5% leaves headroom for the intentional synthetic dirty-rate before it reads as an incident |
| Per-dataset `dq_score` (hard-severity rules only) | **>= 99%** | Hard rules (schema, primary key not-null/unique, referential integrity) are expected to pass near-100%; only soft rules (e.g. the deliberately-dirty `email` field) are allowed to sit lower |
| Quarantine rate (`adls/quarantine/` volume vs. total rows) | **<= 5%** per pipeline run, investigate above this | Current measured rate is ~1.1% for `crm_customer` ([`data_quality/reports/dq_report.json`](../../data_quality/reports/dq_report.json)) |
| MDM `HUMAN_REVIEW` rate (entity resolution) | **<= 10%** of match pairs routed to human review | See [`governance/lgpd.md`](../../governance/lgpd.md) and [ADR-006](../decisions/ADR-006-human-in-the-loop.md) for the human-in-the-loop mechanism this measures |

Diagnosis and resolution for a DQ SLO breach: [`dq_score_drop.md`](dq_score_drop.md).

## 2. Freshness SLOs (pipeline layer)

| Layer transition | Target | Basis |
|---|---|---|
| Bronze (landing → raw ingest) | **<= 1 scheduled run late** before flagged stale | Azure Data Factory batch pulls (CRM/Marketing/Support, Olist) and the Event Hubs streaming consumer are both scheduled/continuous per [ARCHITECTURE.md §5](../../ARCHITECTURE.md#5-layer-2--ingestion) |
| Bronze -> Silver | **<= 4 hours** from Bronze landing to Silver materialization | Databricks Workflow (DABs) job — see [`pipeline_failure.md`](pipeline_failure.md) for the job-failure diagnostic path when this is missed |
| Silver -> Gold | **<= 2 hours** from Silver materialization to Gold availability | Includes MDM Golden Record and DQ checkpoint completion, which gate Gold materialization |
| Gold (Databricks) -> Snowflake CORE sync | **<= 1 hour** | External stage sync described in [ADR-002](../decisions/ADR-002-lakehouse-vs-warehouse.md) |

A freshness SLO breach is diagnosed the same way as a pipeline job failure — start at [`pipeline_failure.md`](pipeline_failure.md).

## 3. Agent / API / Cortex latency SLOs

| Interface | Target (p95) | Target (p99) | Basis |
|---|---|---|---|
| `api/` REST endpoints serving pre-computed metrics (parquet reads from `data/mdm/`, `data/ml/`) | **<= 500ms** | **<= 1.5s** | No live model inference on the request path — see [`api/README.md`](../../api/README.md) |
| Single-tool agent call (one MCP tool invocation, e.g. a DQ lookup) | **<= 3s** | **<= 8s** | Includes LLM Gateway round-trip ([ARCHITECTURE.md §14](../../ARCHITECTURE.md#14-layer-11--llm-gateway--model-selection) region) |
| Multi-step agent orchestration (e.g. Data Quality Agent's diagnose -> quantify -> root-cause flow in [`dq_score_drop.md`](dq_score_drop.md)) | **<= 15s** | **<= 30s** | Multiple chained LLM calls + tool calls; escalate to human-in-the-loop rather than retry indefinitely past this ([ADR-006](../decisions/ADR-006-human-in-the-loop.md)) |
| Snowflake Cortex Analyst / Semantic View query (natural-language -> SQL -> result) | **<= 10s** | **<= 20s** | Evaluated against `snowflake/evaluations/` golden-question set for both latency and correctness ([ARCHITECTURE.md §12](../../ARCHITECTURE.md#12-layer-9--semantic-layer)) |

Metrics backing these targets are the `ml_latency`, `agent_latency`, and `mcp_calls` series exported via OpenTelemetry to Prometheus/Grafana ([ARCHITECTURE.md §17](../../ARCHITECTURE.md#17-layer-14--observability--finops)).

## 4. What happens on a breach

1. The Monitoring Agent (or a human reading the Grafana `Platform Observability` Power BI page — [ARCHITECTURE.md §13](../../ARCHITECTURE.md#13-layer-10--power-bi--semantic-model)) flags the specific metric and layer that breached its target above.
2. Route to the matching runbook: [`dq_score_drop.md`](dq_score_drop.md) for data-quality SLOs, [`pipeline_failure.md`](pipeline_failure.md) for freshness SLOs. Latency SLO breaches on agents/API/Cortex are diagnosed via the OpenTelemetry trace for the specific slow call — check the LLM Gateway's model-selection choice (`agents/llm_gateway/models.yaml`) and MCP tool call count first, since chained tool calls are the most common cause of a multi-step orchestration breach.
3. Log root cause and resolution the same way [`dq_score_drop.md` §"After resolution"](dq_score_drop.md#resolution) describes — a single accountability trail across every runbook, not a separate incident process per layer.

## 5. Revisiting these targets

These numbers are initial targets set for Sprint 16 (Enterprise hardening). They are deliberately not hard-coded into alerting thresholds without also being reviewed periodically — a target that's never missed is usually too loose, and a target missed constantly is either a real problem or miscalibrated. Revisit this table whenever `data_quality/reports/` baselines shift meaningfully, or when a runbook resolution repeatedly cites "expectation itself is miscalibrated" as the root cause.
